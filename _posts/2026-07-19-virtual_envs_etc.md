## virtual environments vs. version managers
A virtual environment, often used in the context of Python, is an isolated setup that keeps a project's software dependencies separate from the rest of the system and other projects. These include things such as an interpreter and location for installed packages, both specific to that one environment. A related concept is the version manager, which manages different versions of a piece of software (e.g. versions of Python itself, packages, etc). Instead of isolating the dependencies, a version manager allows us to choose which version of a programming language, tool, etc to load for a given project.

rbenv, despite what its name implies, is not a virtual environment. Rather, it is a version manager for Ruby: it reads the `.ruby-version` file in a repo to determine which Ruby to use, using shims to do so. Shims are small scripts that are executed every time we call `ruby` or `gem`, responsible for finding a `.ruby-version` file and routing the code execution to the specified Ruby version.

> This means you should never set `PATH=.../<hardcoded-ruby-version>/...` unless you plan on using the same Ruby version across all projects. Instead, we should use rbenv to read `.ruby-version` and dynamically resolve the path when the project loads.
{: .prompt-warning }

Python's venv is an example of a virtual environment, where all versions and dependencies are isolated per project on disk. In contrast, for Ruby, all projects sharing the same Ruby version store their dependencies in the same location on disk. When a project loads, its `Gemfile` tells us which versions of which dependencies to load. This means that two projects using the same Ruby version and the same version of a given gem will point to the same location on disk, whereas with Python venv, they'd point to two separate locations. This is also why we never activate an rbenv the way we do a venv or conda env (i.e., running `source venv/bin/activate` or `conda activate env-name`): rbenv isolates by version and lookup, while venv isolates per project.

> In terms of security and levels of isolation, environment < container < virtual machine. In a nutshell, virtual environments only isolate the software location. Containers create a separate filesystem, PID namespace, etc while sharing the host kernel. VMs have their own OS, filesystem, networking, etc. For the purposes of simple projects without much security risk, a virtual environment is often sufficient.
{: .prompt-info }


## locations on disk: rbenv vs. venv vs. conda environment
- rbenv resolves to the following path: `~/.rbenv/versions/<version-num>/lib/ruby/gems/<version-num>/gems/`. Dependencies are stored in a centralized location, not unique to any project
- conda env resolves to `/opt/anaconda3/envs/<env-name>/lib/<python-version>/site-packages/dependency-name-and-version`. Dependencies are stored in a centralized location, similar to rbenv, but are ultimately still isolated per project since it’s a virtual environment
- Python venv resolves to `project-folder/venv/lib/python-version/site-packages/dependency-name-and-version`. Dependencies are not all stored in a centralized location; rather, the root is the project folder itself

## example: setting up a Ruby environment
1. `brew install rbenv ruby-build`\
   > rbenv is the version manager, ruby-build builds the actual binaries for each Ruby version

   > Don't install Ruby via Homebrew since you want rbenv to manage all our Ruby versions. If you ran `brew install ruby`, it would install Ruby under `/opt/homebrew/...`, which is inaccessible by rbenv.
   {: .prompt-info }

2. `echo 'eval "$(rbenv init - zsh)"' >> ~/.zshrc`\
    > Breaking down this command:
    >
    > - Adds `eval "$(rbenv init - zsh)"` to `~/.zshrc`
    > - Whenever a new shell session starts, that command automatically runs
    > - Specifically, the command that runs is the script generated by `rbenv init - zsh`:
    >
    >   ```bash
    >   export PATH="~/.rbenv/shims:${PATH}"
    >   export RBENV_SHELL=zsh
    >   command rbenv rehash 2>/dev/null
    >   rbenv() {
    >     local command
    >     command="${1:-}"
    >     if [ "$#" -gt 0 ]; then
    >       shift
    >     fi
    >
    >     case "$command" in
    >     rehash|shell)
    >       eval "$(rbenv "sh-$command" "$@")";;
    >     *)
    >       command rbenv "$command" "$@";;
    >     esac
    >   }
    >   ```
    > - This script automatically sets up shims, which then locates the correct Ruby version

   > `$` vs. `eval`:\
   > `$(command)` runs the command as a single subprocess and returns the string result (whatever was printed to stdout). This is useful for getting a single value/piece of data to pass as an argument to another command. Meanwhile, `eval "$command"` parses and handles multi-line scripts, equivalent to entering the commands line by line in the terminal. This is useful for when you have a long shell script as a string and need to run the whole thing.
   {: .prompt-info }

3. `rbenv install <version-number>`\
   > Invokes ruby-build to install the requested Ruby version

4. `cd /path/to/project`

5. `rbenv local <version-number>`\
   > Creates `.ruby-version` so that every time we open up this project in the future, it will automatically locate the correct Ruby version and location to load dependencies from
